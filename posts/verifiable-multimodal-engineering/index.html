Engineering note · Published July 4, 2026 at 09:42 (UTC+8)

Verifiable multimodal engineering systems

When a multimodal system gives the wrong answer, I want to be able to trace it back to the input, the model, and the rules applied at that step. Showing the final result is not enough to locate an error.

From signals to accountable outputs

The projects I work on take different inputs. Infrastructure monitoring combines radar signals with live video; industrial nesting uses cutting instructions and defect images. Agent workflows leave event traces. In each case, someone needs to inspect the result and understand how the system produced it.

Design principle

I prefer to keep intermediate results alongside the final answer. A reviewer should be able to recover the input, identify the model version, and see which constraints were active. That makes it possible to check a disputed result without reconstructing the whole run from memory.

Reusable pattern

I would store each input with its modality and timestamp, rather than keep only the final feature tensor. Learned predictions also need a separate check against the rules or geometry of the task. A plausible-looking nesting layout, for example, still has to satisfy its geometric constraints.

The interface should make relevant alarms, output certificates, and replay logs easy to reach. Saving the model version and active constraints with each result helps another person reproduce a failure.

Learning from failures

A failed nesting layout should point to the geometry constraint it violated. A radar alarm should lead back to the signal segment that triggered it. For an agent, the record should show the step where it used the wrong state. Those details give me a place to begin the next revision.
