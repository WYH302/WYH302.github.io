Verifiable multimodal engineering systems

Multimodal systems become more useful when users can trace each output through constraints, intermediate artifacts, and explicit decision rules.

From signals to accountable outputs

Several project lines share the same engineering pattern: raw inputs arrive from different modalities, then the system must produce a result that a human can inspect. Examples include radar signals and live video in infrastructure monitoring, natural-language cutting orders and defect images in industrial nesting, or event traces in agentic workflows.

Design principle

When a system fails, I want to follow the result back to its inputs and decisions. There should be a record of which model identified a defect, which rule accepted a layout, and what was changed later. A fluent explanation beside a final answer does not show whether that explanation matches the computation.

Consider a hypothetical stone-nesting task. An order calls for pieces of specified dimensions while avoiding defects marked in a photograph. The first steps are to confirm units, the scale between image and material, and defect boundaries. “Use as little material as possible” also needs an objective that can be compared. Without those decisions, a tidy layout may solve the wrong problem.

A candidate layout can then be checked for pieces outside the slab, overlaps, the agreed cutting clearance, and entry into excluded regions. If a check fails, the interface should identify the piece and constraint and retain the failed layout. Running the same checks after a revision shows whether the problem was resolved or merely hidden by a different drawing.

Reusable pattern

I would keep the necessary provenance by modality and timestamp, with the model version and active constraints attached to each result. Separating learned judgments from rule-based or geometry checks makes errors easier to locate. Output certificates, alarms, traces, or replay logs should be accessible beside the final interface, so users can follow a result back to its computation without finding a separate internal account.

What a passed check still needs to say

I want a check to state its scope. “This layout satisfies the current defect mask and cutting-clearance constraints” tells a user more than an isolated “verified” badge. It identifies assumptions still worth confirming: whether the mask is complete, whether the clearance suits the equipment, and whether the input describes the current slab.

If an operator changes a defect boundary, the old layout and check should be invalidated together or clearly retained as records for the old input. The system needs to recompute and show what the edit affects. I do not want auditability to matter only after an incident. Making these dependencies visible during ordinary use can help someone notice that they are relying on a stale result.

Learning from failures

One boundary remains in this design example: passing every geometry check does not establish that the defects were identified correctly. Inspection of the original image or material may still be needed. Separating recognition errors, unit errors, and layout errors tells us whether to change the model, the interface, or the constraints.

The same questions apply elsewhere. A radar alarm needs its signal segment and corresponding video time. An agent acting on the wrong state needs a trace of when that state was read. Nor should logs be kept without limit: sensitive inputs need access restrictions and a retention period. I want the next person investigating a failure to have somewhere concrete to start, rather than more records for their own sake.
