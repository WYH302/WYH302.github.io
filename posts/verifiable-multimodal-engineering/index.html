Engineering note | 2026-07-03

Verifiable multimodal engineering systems

Multimodal systems become more useful when users can trace each output through constraints, intermediate artifacts, and explicit decision rules.

From signals to accountable outputs

Several project lines share the same engineering pattern: raw inputs arrive from different modalities, then the system must produce a result that a human can inspect. Examples include radar signals and live video in infrastructure monitoring, natural-language cutting orders and defect images in industrial nesting, or event traces in agentic workflows.

Design principle

The system should expose enough structure that a reader can ask: which input produced this output, which constraint was active, which model made the prediction, and what artifact can be audited afterward? This is why I prefer pipelines that preserve intermediate results rather than only showing a final generated answer.

Reusable pattern

  • Represent inputs by modality and timestamp, not just by final feature tensors.
  • Separate learned inference from rule-based or geometric feasibility checks.
  • Keep output certificates, alarms, traces, or replay logs close to the final interface.
  • Describe contribution and evidence type plainly when presenting the system publicly.

Academic value

Verifiability changes how a project reads. It makes the work less like a demo and more like a research object: something with a problem setting, assumptions, constraints, implementation decisions, and inspectable outputs. That is the standard I want this website's project page to reflect.
